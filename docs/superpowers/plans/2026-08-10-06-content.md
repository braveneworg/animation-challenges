# Content Batches Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Author the remaining 106 challenges of the spec §4.1 manifest (123 planned − 17 already in the registry) in fourteen dependency-ordered batches, complete all six cross-technique series, and finish by flipping the catalog integrity ceilings to per-category equality — the drift guard deliberately left open since Plan 01.

**Architecture:** Each challenge is one typed module (`src/challenges/<category>/<slug>.ts`) the registry glob collects automatically, plus — for `auto`/`hybrid` grade modes — a sibling `<slug>.grade.ts` the sandbox glob collects. Nothing is wired by hand, and **no UI work exists in this plan at all**: Plan 05's contract ("The zero-UI-work guarantee") promises that a dropped challenge module appears in the catalog, workspace route, dashboard math, and series links mechanically. Every batch lands as one commit gated by `pnpm verify` (which includes `pnpm test:catalog` — spec §8.2 rules 3/5/6 enforced per challenge, mechanically).

**A scoping decision, stated openly:** unlike Plans 01–05, the tasks in this plan do NOT contain the complete source text of all 106 challenges — pre-writing ~212 files of challenge content and grader code inside a planning document would do the work in the wrong artifact, at absurd length. This plan is instead the **production system** for that content: (1) batch tasks that carry every §4.1 manifest item verbatim with an exact per-challenge authoring card (id, shape, behavioural contract with exact numbers, grader design and its discriminating failure); (2) one per-challenge checklist every batch is executed against; (3) three fully-worked exemplar challenges — complete module + grader code, zero placeholders — chosen to cover authoring situations Plan 03's sixteen did not demonstrate; (4) the final equality flip with a mutation check. An implementer executing a batch task has, between their task's cards, the checklist, the three exemplars, and Plan 03's committed contract (the authoring manual, with sixteen proven graders on disk to copy), everything needed to write each challenge without further decisions of substance.

## Global Constraints

- **No `any` type.** Enforced by `typescript/no-explicit-any` in oxlint.
- **No lint disable comments** in any spelling. Enforced by `pnpm lint:no-disable`.
- **No `as` type assertions on values you do not control** (`typescript/no-unsafe-type-assertion`). Narrow `unknown` with `typeof` / `in` / `instanceof` checks.
- **No `await` inside loop syntax** — `eslint(no-await-in-loop)` is an error repo-wide. Sequential async stepping uses `forEachStep` from `@/sandbox/grader-utils` (standing lesson 8). Every sampling loop in this plan is written with it.
- **Optional interface properties are `prop?: T | undefined`** (`exactOptionalPropertyTypes`).
- **Prettier:** printWidth 120, single quotes, trailing commas, semicolons, sorted imports. Run `pnpm format` before every commit.
- **Commits:** Conventional Commits, atomic (one per batch task), on branch `feat/animation-challenges-platform`. Never commit to `main`. No AI attribution or `Co-authored-by` lines. `pnpm verify` green before every commit.
- **`goals` are grader inputs, not prose** (standing lesson 3 — the Plan 01 defect class). Every goal literally true of the reference solution; every auto-checkable goal mapped to ≥1 assertion; numbers stated in goals are the numbers the grader asserts. Rules 5/6 catch violations mechanically, but write it right the first time: checklist item C1 is a required pre-commit audit in every batch.
- **Starters must genuinely fail their grader** (spec §8.2 rule 6) with at least one hinted failing assertion or a throw. The best starters *partially* work — the failing assertions then teach the exact missing concept.
- **Never string-compare a computed `transform`.** `ctx.matrix(el)` (a `DOMMatrix`) and component epsilons, always. The same discipline extends to WAAPI keyframes: assert computed state at seeked times, never authored keyframe strings.
- **No compound media queries anywhere in challenge CSS/JS or graders** (Plan 02 caveat): `patchMatchMedia` answers only the `prefers-reduced-motion` clause. Single-clause `(prefers-reduced-motion: …)` queries only; Tailwind's `motion-safe:`/`motion-reduce:` variants compile to single-clause queries and are safe.
- **No test or grader assertion coupled to absolute catalog counts** (standing lesson 7) — except Task 15, which is the one sanctioned equality task. Batch tasks derive any expected count from the entities the batch itself owns (its own ids), never from the registry total.
- **Mutation checks must fail deterministically** (standing lesson 6): no mutation whose RED depends on accumulated float time landing on either side of a boundary. Where a batch's mutation check involves frame sums, the check overshoots by whole frames or breaks two guards at once; each task's mutation step states its arithmetic.
- **`relatedIds` reference only challenges that exist at commit time.** Members landed in the same batch commit may reference each other; anything else must already be on disk. The task ordering below exists to make every listed `relatedIds` value legal.
- **The integrity ceilings stay ceilings until Task 15.** No earlier task touches `src/challenges/integrity.ts` or the real-registry integrity binding.
- **All commands run from the repo root via relative paths.** The repo is public: no personal absolute paths, nothing secret-shaped, in any file.

## The per-challenge checklist (referenced by every batch task as C1–C12)

Every challenge in every batch is authored against ALL of these. The batch's final audit step walks each new challenge through the list; a batch is not committable with any item unchecked.

- **C1 — Goal→assertion map.** Before the grader is written, tabulate every goal against the assertion(s) that will check it (or against a `rubric` item id for perceptual goals — hybrid only). After the grader is written, re-read the map against the code AND re-read every goal against the solution files: each goal literally true, each number in a goal the same number the grader asserts. This is the discipline that prevents the Plan 01 hover-lift defect; rules 5/6 are the mechanical backstop, not the substitute. Where a card's sample code and its goal→assertion map disagree, the map governs (Plan 03 ratified precedent: the missing assertion gets added; the sample is the defect).
- **C2 — The starter genuinely fails.** Run the mental starter-vs-grader trace before `pnpm test:catalog` does it for real: which assertion fails first, and does its `hint` teach the missing concept? Prefer starters that partially work (the card's Contract line says what the starter already does).
- **C3 — The solution passes clean.** Zero failing assertions, no throw, no timeout, within `graderTimeoutMs ?? 5000`.
- **C4 — Hints.** Exactly 3, progressive: concept → shape → exact code. The third hint may contain the load-bearing line of the solution.
- **C5 — Explanation.** Markdown, `### Why this works` first, then the pitfall, then the pattern/series comparison. Series members' explanations explicitly compare against their siblings by id.
- **C6 — Naming and files.** Kebab-case slug = filename; `id` exactly `<categoryId>/<slug>`. Runtime file rules: `dom` → `index.html` **fragment** + optional `.css` + `index.ts` (required iff any script file exists); `react` → `App.tsx` default-exporting a plain function component; `module` → `index.ts`, nothing rendered. Starter and solution declare the same file names and differ in content. Sources authored as arrays of single-quoted lines `.join('\n')` (double-quoted where a line contains an apostrophe). The file the user should edit comes first in the object literal (Plan 05: tab order).
- **C7 — Series and relatedIds bookkeeping.** `relatedIds` resolve at commit time (same-commit ids allowed); no self-reference. Series members carry `series: { id, label }` with the label copied exactly from `SERIES`; the three members sit in three distinct categories.
- **C8 — Toolchain.** No `any`, no disable comments, no unsafe assertions (`in`/`typeof`/`instanceof` narrowing only), no `await` in loop syntax (`forEachStep`), `prop?: T | undefined`, Prettier-clean at printWidth 120.
- **C9 — Grader discipline.** `throw` only when required starter markup is missing; otherwise a hinted failing `ctx.expect` and early `return` when later assertions would be noise. Every `hint` names the exact property/utility/API that fixes the failure. DOMMatrix component reads, never transform strings. Epsilons: positions 0.5–2px (up to 8 for long SVG offsets), scales/opacity 0.02–0.05, pure math 1e-9; exact `===` for durations a goal states exactly.
- **C10 — Timing and determinism.** Durations 250–1200ms. CSS/WAAPI state via `seek`/`styleAt`/`settle`; rAF and motion-JS (springs, layout, exit) via `stepFrames` (n = n frames); scroll timelines via `scrollTo` ONLY — never seek/settle a scroll-timeline animation. Infinite animations are never settled. No challenge depends on `setTimeout`/`setInterval` for graded animation (the virtual clock does not patch timers). `graderTimeoutMs: 10_000` iff the grader samples frames with `stepFrames(1)` loops; omitted otherwise. Motion-specific (Plan 03 findings): vanilla `animate()` defers the real `element.animate()` behind motion's internal rAF batch, which only `stepFrames` drains — one `await ctx.time.stepFrames(1)` before the animation-existence check is the sanctioned pattern (`seek`/`settle` cannot flush it). Motion springs currently take the JS/rAF path (stepFrames-drivable), not the WAAPI fast path; a future Motion upgrade flips affected graders to a loud rule-5 failure, not a silent pass.
- **C11 — Metadata bands.** `estimatedMinutes`: guidance bands novice 5–8, intermediate 10–15, advanced 15–25, expert 25–40 — the card's per-challenge value is authoritative even when it exceeds its band (Plan 03 ratified precedent: an honest estimate is never clamped to the band). `tags`: 2–5 lowercase kebab terms. `tech` drawn from the card.
- **C12 — Count hygiene.** After the batch, per-category totals stay ≤ `plannedCount` (ceilings until Task 15). No new test file; no assertion anywhere derived from the registry's absolute size.

## Batch execution protocol (the TDD cycle every batch task runs)

Every batch task executes this exact cycle; the task text below adds only what is batch-specific (cards, mutation checks, expected failure lists, commit message).

1. **Author the challenge modules** from the task's cards, one `src/challenges/<category>/<slug>.ts` per card, following C4–C7/C11 for everything the card does not spell out. Rubric cards get a `rubric` array and no grader; hybrid cards get both.
2. **Watch the gate demand the graders.** Run `pnpm test:catalog`. Expected: FAIL — the grader-file⇔gradeMode suite reports every new `auto`/`hybrid` id as missing its grader (and rule 5 reports `no grader is registered for "<id>"`). Rule 3 (both file sets transpile) must already PASS for every new id; fix transpile failures now. This is the observed failing state of content TDD.
3. **Write the graders** from the cards' Grade lines, each starting from the named template file on disk, completing the C1 map per challenge as you go.
4. **Run `pnpm test:catalog` — green.** Every new id passes rules 3/5/6 and the grader-file rule. Runtime grows ~1–2.5s per auto/hybrid challenge (two grading mounts each run).
5. **Mutation checks** — run the batch task's named mutations one at a time: apply, run `pnpm test:catalog`, capture the named failure, restore. A mutation that does not fail as predicted is a stop-the-line defect in the grader (standing lesson 1).
6. **Audit** — walk every new challenge through C1–C12.
7. **Verify and commit:**

```bash
pnpm format && pnpm verify
git add src/challenges
git commit -m "<the task's commit message>"
```

## How to read an authoring card

Each card fully determines one challenge:

- The heading gives the id, the §4.1 item (category + item number + **verbatim manifest title**), and difficulty (N/I/A/X).
- **Shape:** runtime · gradeMode · `tech` array · series membership · `graderTimeoutMs` if required.
- **Contract:** the behavioural spec — what the starter already does, what the solution does, with the exact numbers the goals will state and the grader will assert (the card's numbers are binding; C1 makes them identical in goals and grader).
- **Grade:** the template grader file to copy (all templates exist on disk from Plans 02/03 or earlier tasks of this plan), the assertion outline, and the **discriminator** — the assertion(s) the starter must fail.
- **relatedIds:** the exact array to ship (every id already exists per the task ordering).

#### `css-transitions/compositor-move` — §4.1 css-transitions 2: "Replace `width`/`left` animation with compositor-only properties" [N]
- **Shape:** dom · auto · tech `['css']`
- **Contract:** Starter: a `.box` (160×80px, `position: relative`) that on `.box:hover` transitions `left: 0 → 200px` and `width: 160px → 200px` over 300ms — it moves, with the wrong properties. Solution: identical visual result via `transform: translateX(200px) scaleX(1.25)` with `transition: transform 300ms ease-out`; `left`/`width` never mentioned. Goals state: 200px travel, 1.25× horizontal growth, 300ms, and "computed `left` and `width` never change".
- **Grade:** template `css-transitions/hover-lift.grade.ts`. Hover → find the `CSSTransition` by `transitionProperty === 'transform'`; `seek(150)` mid-flight: `matrix(box).e` strictly between 20 and 180 AND `computed(box, 'left')` equals its pre-hover reading AND `pxNumber(computed(box, 'width')) === 160`; `settle()`: `matrix.e ≈ 200` (ε 1), `matrix.a ≈ 1.25` (ε 0.02). **Discriminator:** the starter has no transform transition (transform assertions fail) and its mid-flight `left`/`width` readings change (the two "never change" negatives fail).
- **relatedIds:** `['css-transitions/hover-lift']`

#### `css-transitions/per-property-timing` — §4.1 css-transitions 3: "Per-property durations and delays on one element" [I]
- **Shape:** dom · auto · tech `['css']`
- **Contract:** A `.chip` where hover animates two properties on different schedules from ONE `transition` list: `transform` (translateY(-12px)) 400ms delay 0ms, `background-color` 200ms delay 400ms — the colour change waits for the move to finish. Starter: `transition: all 400ms` (both move together — works, but the choreography is wrong).
- **Grade:** hover → two `CSSTransition`s; for the transform one `timingOf` gives `duration === 400`, `delay === 0`; for the background-color one `duration === 200`, `delay === 400`. `seek(200)`: `matrix.f` strictly between −11 and −1 (mid-move) while `computed(chip, 'background-color')` still equals the pre-hover colour; `seek(500)`: `matrix.f ≈ −12` (ε 0.5) and background mid-change (not equal to either endpoint). **Discriminator:** starter's `all` produces a background-color transition with `delay === 0` (delay assertion fails) and a changed colour at `seek(200)` (the "colour waits" negative fails).
- **relatedIds:** `['css-transitions/compositor-move']` (same commit)

#### `css-transitions/auto-height` — §4.1 css-transitions 4: "Transition to `auto` height via the `grid-template-rows: 0fr→1fr` trick" [A]
- **Shape:** dom · auto · tech `['css', 'ts']`
- **Contract:** A disclosure: `.trigger` button + `.panel` wrapper around `.panel-inner` (text content, intrinsic height). `index.ts` (IDENTICAL in starter and solution — the CSS is the challenge) toggles `.open` on the wrapper on click. Starter CSS: `height: 0 → height: auto` on `.open` — the panel snaps (auto is not interpolable). Solution: wrapper `display: grid; grid-template-rows: 0fr; transition: grid-template-rows 300ms ease-out`, `.open { grid-template-rows: 1fr }`, inner `min-height: 0; overflow: hidden`.
- **Grade:** measure `panel-inner.getBoundingClientRect().height` before click (≈0, ε 1); `click(trigger)`; assert a `CSSTransition` with `transitionProperty === 'grid-template-rows'` exists; `seek(150)`: inner rect height strictly between 4px and (full − 4px), where full = the inner element's `scrollHeight` (intrinsic height, readable regardless of the grid track); `settle()`: rect height ≈ scrollHeight (ε 2). **Discriminator:** starter creates no grid-template-rows transition (assertion fails) and its mid-flight height equals the full height already (snap).
- **relatedIds:** `['css-transitions/per-property-timing']` (same commit)

#### `css-transitions/display-entrance` — §4.1 css-transitions 5: "`transition-behavior: allow-discrete` + `@starting-style` for `display` entrances" [A]

```ts
  title: 'Diagnose and fix a layout-thrashing animation',
  categoryId: 'performance',

    'page six times. Open the loop in `index.ts`: for every bar, every frame, it reads `offsetWidth`',
    '(forcing a synchronous layout) and then writes `style.width` (dirtying layout again for the next',
    'read). Read → write → read → write: the classic thrash.',
    '',
    'Fix it without changing what the user sees: each bar still sweeps from nothing to its full 240px',
    'over 600ms, staggered 60ms apart. Move the motion to `transform: scaleX()`, fix the bar length in',
    'CSS, and stop reading layout inside the loop entirely.',
  ].join('\n'),
  goals: [
    'Each bar still sweeps in: from zero length to its full 240px over 600ms, with a 60ms stagger per bar.',

      'const start = performance.now();',

      '',

      '  <div class="bar"></div>',
      '  <div class="bar"></div>',
```

Create `src/challenges/performance/layout-thrash.grade.ts`:

```ts
import type { GradeContext } from '@/sandbox/grade-context';
import { forEachStep } from '@/sandbox/grader-utils';

const BAR_COUNT = 6;
const FULL_LENGTH = 240;
/** 66 frames = 1100ms at 60Hz — past the last bar's 300ms stagger plus its 600ms sweep. */
const SAMPLE_FRAMES = 66;

/**
 * Grades `performance/layout-thrash`: the bars must still sweep (240px, 600ms, 60ms stagger), the
 * motion must be transform-only (computed width constant), and — the point of the challenge — the
 * frame loop must not read layout. The grader counts forced-layout reads by instrumenting
 * `offsetWidth` and `getBoundingClientRect` on the prototypes, measuring through the captured
 * natives so its own reads are never counted, and restores both in a `finally`.
 */
export async function grade(ctx: GradeContext): Promise<void> {
  const bars = ctx.queryAll('.bar');
  if (bars.length !== BAR_COUNT) {
    throw new Error(`the grader needs the ${BAR_COUNT} .bar elements from the starter markup — keep them intact`);
  }
  const first = bars[0];
  const last = bars[BAR_COUNT - 1];
  if (first === undefined || last === undefined) {
    throw new Error('unreachable: bar count was checked above');
  }

  const offsetWidthDescriptor = Object.getOwnPropertyDescriptor(HTMLElement.prototype, 'offsetWidth');
  const offsetWidthGetter = offsetWidthDescriptor?.get;
  const nativeGetRect = Element.prototype.getBoundingClientRect;
  if (offsetWidthDescriptor === undefined || offsetWidthGetter === undefined) {
    throw new Error('unexpected environment: HTMLElement.prototype.offsetWidth has no getter to instrument');
  }

  function measure(el: Element): number {
    return nativeGetRect.call(el).width;
  }

  let layoutReads = 0;
  Object.defineProperty(HTMLElement.prototype, 'offsetWidth', {
    configurable: true,
    get(this: HTMLElement): number {
      layoutReads += 1;
      const value: unknown = offsetWidthGetter.call(this);
      return typeof value === 'number' ? value : Number.NaN;
    },
  });
  Element.prototype.getBoundingClientRect = function instrumentedRect(this: Element): DOMRect {
    layoutReads += 1;
    return nativeGetRect.call(this);
  };

  const firstLengths: number[] = [];
  const lastLengths: number[] = [];
  const widthReadings: string[] = [];
  try {
    await forEachStep(SAMPLE_FRAMES, async (index) => {
      await ctx.time.stepFrames(1);
      firstLengths.push(measure(first));
      lastLengths.push(measure(last));
      if (index === 5 || index === 20) widthReadings.push(ctx.computed(first, 'width'));
    });
  } finally {
    Object.defineProperty(HTMLElement.prototype, 'offsetWidth', offsetWidthDescriptor);
    Element.prototype.getBoundingClientRect = nativeGetRect;
  }

  const early = firstLengths.at(5) ?? Number.NaN; // ~100ms: bar 0 mid-sweep
  const lastAtStart = lastLengths.at(2) ?? Number.NaN; // ~50ms: bar 5 still inside its 300ms stagger
  const settledFirst = firstLengths.at(-1) ?? Number.NaN;
  const settledLast = lastLengths.at(-1) ?? Number.NaN;

  ctx.expect(early > 8 && early < FULL_LENGTH - 8, {
    message: 'Mid-sweep, the first bar is genuinely mid-length',
    hint: 'Drive progress from elapsed time: scaleX(progress) with progress = clamp(elapsed / 600, 0, 1).',
    actual: `${early.toFixed(1)}px at ~100ms`,
    expected: `strictly between 8 and ${FULL_LENGTH - 8}px`,
  });
  ctx.expectClose(settledFirst, FULL_LENGTH, 2, {
    message: 'The first bar ends at its full 240px length',
    hint: 'The sweep ends at scaleX(1) — full length, reached at 600ms.',
  });
  ctx.expectClose(settledLast, FULL_LENGTH, 2, {
    message: 'The last bar also completes its sweep',
    hint: 'Each bar runs the same 600ms sweep, offset by index * 60 ms.',
  });
  ctx.expect(lastAtStart < 8, {
    message: 'The stagger is real: at ~50ms the last bar has not started yet',
    hint: 'Offset each bar by index * 60 ms before its sweep begins.',
    actual: `${lastAtStart.toFixed(1)}px`,
    expected: 'under 8px while its 300ms stagger delay is still running',
  });

  const [widthEarly, widthLate] = widthReadings;
  ctx.expect(widthEarly !== undefined && widthEarly === widthLate, {
    message: 'Computed `width` never changes while the bars sweep — the motion is all transform',
    hint: 'Fix the bars at width: 240px in CSS and animate scaleX instead of writing style.width.',
    actual: `width read ${widthEarly ?? 'n/a'} then ${widthLate ?? 'n/a'}`,
    expected: 'the same computed width at both samples',
  });

  ctx.expect(layoutReads <= BAR_COUNT, {
    message: 'While the bars sweep, layout is read at most once per bar — never per frame',
    hint: 'Stop reading offsetWidth inside the rAF loop; the bar length is a constant you already know.',
    actual: `${layoutReads} forced layout read(s) during ${SAMPLE_FRAMES} animated frames`,
    expected: `at most ${BAR_COUNT}`,
  });
}
```

```ts
/** Effective uniform scale: the transform matrix times the individual `scale` property (if set). */
function scaleOf(ctx: GradeContext, el: Element): number {
  const individual = ctx.computed(el, 'scale');
  const parsed = individual === 'none' || individual === '' ? 1 : pxNumber(individual);
  const base = Number.isNaN(parsed) ? 1 : parsed;
  return base * ctx.matrix(el).a;
}

/**
 * Grades `motion-presence/exit-fade`: after the toggle the card must still be mounted and animating
 * out (AnimatePresence + exit), be genuinely mid-fade AND mid-shrink at ~200ms, unmount when the
 * exit completes, and replay its entrance on re-show. Exits are JS-driven by motion, so the virtual
 * clock advances them one stepFrames(1) at a time; presence is proven frame-by-frame, not assumed.
 */
export async function grade(ctx: GradeContext): Promise<void> {
  const toggle = ctx.query('.toggle');
  if (toggle === null) {
    throw new Error('the grader needs the `.toggle` button from the starter markup — keep its class name');
  }

  const card = ctx.query('.card');
  ctx.expect(card !== null, {
    message: 'The card starts visible',
    hint: "Keep the starter's initial state: `shown` begins true and the card renders.",
  });
  if (card === null) return;

  await ctx.time.stepFrames(ENTRANCE_FRAMES); // let the entrance finish before testing the exit

  await ctx.click(toggle);
  await ctx.time.stepFrames(1);

  const exiting = ctx.query('.card');
  ctx.expect(exiting !== null, {
    message: 'One frame after hiding, the card is still in the DOM, animating out',
    hint: 'Wrap the conditional in `<AnimatePresence>` and give the motion.div an `exit` target — without them React unmounts instantly.',
  });
  if (exiting === null) return;

  const opacities: number[] = [];
  const scales: number[] = [];
  let unmountedAtSample = -1;
  await forEachStep(EXIT_SAMPLE_FRAMES, async (index) => {
    await ctx.time.stepFrames(1);
    const current = ctx.query('.card');
    if (current === null) {
      unmountedAtSample = index;
      return false;
    }
    opacities.push(pxNumber(ctx.computed(current, 'opacity')));
    scales.push(scaleOf(ctx, current));
    return true;
  });

  const midOpacity = opacities.at(11) ?? Number.NaN; // sample 11 ≈ 216ms into the 400ms ease-out fade
  ctx.expect(midOpacity > 0.05 && midOpacity < 0.85, {
    message: 'Mid-exit the card is genuinely mid-fade',
    hint: 'Animate the exit over time: `exit={{ opacity: 0, scale: 0.8 }}` with the 400ms transition — not a bare conditional.',
    actual: Number.isNaN(midOpacity) ? 'card already gone at ~200ms' : midOpacity.toFixed(3),
    expected: 'opacity strictly between 0.05 and 0.85 at ~200ms',
  });

  const midScale = scales.at(11) ?? Number.NaN; // same sample: the shrink runs alongside the fade
  ctx.expect(midScale > 0.82 && midScale < 0.99, {
    message: 'Mid-exit the card is genuinely mid-shrink toward scale 0.8',
    hint: 'The exit mirrors the entrance: include `scale: 0.8` in the exit target alongside the opacity.',
    actual: Number.isNaN(midScale) ? 'card already gone at ~200ms' : midScale.toFixed(3),
    expected: 'scale strictly between 0.82 and 0.99 at ~200ms (the reference reads ~0.86 there)',
  });

  ctx.expect(unmountedAtSample >= 0, {
    message: 'When the exit finishes, the card unmounts — gone from the DOM, not parked invisible',
    hint: 'AnimatePresence removes the child once its exit completes; do not render it at opacity 0 yourself.',
    actual:
      unmountedAtSample === -1
        ? `still mounted after ${EXIT_SAMPLE_FRAMES} sampled frames (~667ms)`
        : `unmounted at sample ${unmountedAtSample} (~${Math.round((unmountedAtSample + 2) * 16.7)}ms)`,
    expected: 'unmounted within the sampled window',
  });

  await ctx.click(toggle);
  await ctx.time.stepFrames(1);
  const reentering = ctx.query('.card');
  ctx.expect(reentering !== null, {
    message: 'Toggling again brings the card back',
    hint: 'The toggle drives one boolean; showing re-renders the motion.div inside AnimatePresence.',
  });
  if (reentering === null) return;

  const earlyOpacity = pxNumber(ctx.computed(reentering, 'opacity'));
  ctx.expect(earlyOpacity < 0.6, {
    message: 'The re-entrance replays the fade — one frame in, the card is not yet fully opaque',
    hint: 'Keep `initial={{ opacity: 0, scale: 0.8 }}` so every fresh mount starts the entrance from scratch.',
    actual: earlyOpacity.toFixed(3),
    expected: 'opacity below 0.6 one frame after remount',
  });

  await ctx.time.stepFrames(ENTRANCE_FRAMES);
  const settled = ctx.query('.card');
  const settledOpacity = settled === null ? Number.NaN : pxNumber(ctx.computed(settled, 'opacity'));
  ctx.expectClose(settledOpacity, 1, 0.02, {
    message: 'The re-entered card settles fully opaque',
    hint: 'Animate to `opacity: 1` and let the 400ms tween finish.',
  });
}
```

```ts
import type { GradeContext } from '@/sandbox/grade-context';

type StartViewTransitionFn = typeof document.startViewTransition;

/**
 * Grades `view-transitions/dom-swap`. The grader wraps `document.startViewTransition` BEFORE
 * clicking so it can prove the swap runs through the API (and capture the ViewTransition object),
 * delegates to the native method so the transition genuinely runs, asserts the browser-generated
 * `::view-transition` pseudo-element animations exist after `ready`, awaits `finished` (real time —
 * the compositor drives the crossfade; the virtual clock does not apply), and restores the method
 * in a `finally` by deleting the instance shadow.
 */
export async function grade(ctx: GradeContext): Promise<void> {
  const button = ctx.query('.swap');
  const panel = ctx.query('.panel');
  if (button === null || panel === null) {
    throw new Error(
      'the grader needs the `.swap` button and `.panel` element from the starter markup — keep both class names',
    );
  }

  const supported = typeof document.startViewTransition === 'function';
  ctx.expect(supported, {
    message: 'The grading browser supports the View Transitions API',
    hint: 'Grading runs in Chromium, where `document.startViewTransition` exists. If this fails, the sandbox environment is broken — not your code.',
  });
  if (!supported) return;

  const before = panel.textContent?.trim() ?? '';
  ctx.expect(before === 'Day', {
    message: 'The panel starts on the Day scene',
    hint: 'Keep the starter markup: the panel begins as data-scene="day" with the text "Day".',
    actual: before,
    expected: 'Day',
  });

  const native: StartViewTransitionFn = document.startViewTransition.bind(document);
  let calls = 0;
  let sceneAtCall = '';
  let captured: ReturnType<StartViewTransitionFn> | null = null;
  const wrapped: StartViewTransitionFn = (...args: Parameters<StartViewTransitionFn>) => {
    calls += 1;
    sceneAtCall = panel.textContent?.trim() ?? '';
    const transition = native(...args);
    captured = transition;
    return transition;
  };
  document.startViewTransition = wrapped;

  try {
    await ctx.click(button);

    ctx.expect(calls === 1, {
      message: 'Clicking Swap starts exactly one view transition',
      hint: 'Wrap the mutation: `document.startViewTransition(() => { swapScene(); })` inside the click handler.',
      actual: calls,
      expected: 1,
    });
    if (captured === null) return;
    const transition: ReturnType<StartViewTransitionFn> = captured;

    ctx.expect(sceneAtCall === 'Day', {
      message: 'The mutation happens inside the update callback — the page still shows Day at the moment the transition starts',
      hint: 'Do not swap first and then call startViewTransition: the API snapshots the OLD page before running your callback, so the swap goes inside.',
      actual: sceneAtCall,
      expected: 'Day',
    });

    await transition.ready;

    const pseudoAnimations = document.documentElement.getAnimations({ subtree: true }).filter((animation) => {
      const effect = animation.effect;
      return effect instanceof KeyframeEffect && (effect.pseudoElement?.startsWith('::view-transition') ?? false);
    });
    ctx.expect(pseudoAnimations.length > 0, {
      message: 'While the transition runs, the browser is animating the ::view-transition snapshot pseudo-elements',
      hint: 'The default crossfade between old and new snapshots comes free once the mutation runs inside startViewTransition.',
      actual: `${pseudoAnimations.length} pseudo-element animation(s)`,
      expected: 'at least one ::view-transition-old/-new animation',
    });

    await transition.finished;

    const after = ctx.query('.panel')?.textContent?.trim() ?? '';
    ctx.expect(after === 'Night', {
      message: 'When the transition finishes, the panel shows the swapped scene',
      hint: 'The update callback must still perform the swap — startViewTransition animates your change, it does not make it.',
      actual: after,
      expected: 'Night',
    });
  } finally {
    Reflect.deleteProperty(document, 'startViewTransition');
  }
}
```
